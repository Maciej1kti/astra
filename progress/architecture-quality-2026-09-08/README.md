## What is already worth keeping

- The dependency direction: transport/application depend on the domain and store;
  the domain has no HTTP or filesystem dependency.
- Source-authoritative writes, version checks, durable journals, replay identity
  and recovery. Their complexity serves explicit requirements.
- Schema validation and generated TypeScript. `Validated<T>` already provides a
  useful construction boundary, even though callers do not consistently retain it.
- Existing focused helpers: `ReadRequests`, pagination, route serialization,
  editor payload translation, date adapters and gesture handling. These provide
  good starting points for further extraction.
- Native dialogs, bounded data loading, lazy planning imports and real transport/
  durability regressions. No replacement framework or general plugin architecture
  is justified by this review.

## Prioritized findings

### 1. Give command execution one implementation and explicit states

**Priority: high.** Evidence:
[DateChange](../../apps/web/src/features/planning/DateChange.svelte#L72),
[MoveChange](../../apps/web/src/features/board/MoveChange.svelte#L75),
[CardUpdateComposer](../../apps/web/src/features/cards/CardUpdateComposer.svelte#L75),
[Editor](../../apps/web/src/features/editor/Editor.svelte#L530),
[Settings](../../apps/web/src/features/settings/Settings.svelte#L163) and
[TagManager](../../apps/web/src/features/tags/TagManager.svelte#L178).

These components independently combine `pending`, `busy`, errors, session access,
definitive rejection, retries and completion callbacks. The common `command()`,
`send()` and `commandStatus()` helpers correctly preserve wire identity, but the
state transitions above them are repeated. Some components offer a status check;
others guide the user through replay. A protocol correction must therefore be
reviewed in several UI implementations. Session-ended events occur in 14 frontend
source files; four components directly await `commandStatus()`.

Extract a small per-operation command controller with a pure transition core:
idle, submitting, uncertain, committed and rejected, retaining server states such
as blocked/needs-review explicitly. Keep session availability orthogonal to the
command outcome. Preserve the existing immutable payload, request ID, original
epoch and expected version throughout retry and reconnection.

Keep feature-specific outcomes in each feature: refreshing focus, showing a date
conflict, clearing a report draft and progressing a registration job are different
behaviors. A tag batch needs independent command instances for its rows. Avoid a
single global pending command or a configurable universal workflow engine.

Also replace
[`CommandReply = Partial<...>`](../../apps/web/src/lib/api/api.ts#L199): it admits an
empty object and erases `status`, so successful completion is often inferred from
the absence of `state`. The generated contracts already distinguish committed/
noop responses, running jobs and command status. Normalize those variants at the
client boundary with explicit discriminants, preserving accepted-job handling.

**Done when:** consumers no longer duplicate transport-state transitions, and
tests cover lost responses, definitive rejection, session loss/reconnection,
original-epoch retries, conflicts and accepted jobs through the shared controller.

### 2. Make App.svelte the composition root, with separate owners for live state

**Priority: high.** Evidence:
[state declarations](../../apps/web/src/App.svelte#L105),
[refresh orchestration](../../apps/web/src/App.svelte#L375),
[SSE connection](../../apps/web/src/App.svelte#L502),
[navigation and draft guards](../../apps/web/src/App.svelte#L634).

`App.svelte` has 2,235 lines: 814 inside its script and 856 inside its style block.
The script contains 54 `$state` calls. Total length overstates executable
complexity, but the responsibilities are still substantial: pairing, session
cleanup, routing, pagination, request generations, SSE batching, lazy views,
editor navigation guards and workspace rendering.

`view-queries.ts` already describes reads and invalidations. The next useful step
is to extract the state that executes that policy, rather than adding more stateless
helpers while leaving every lifecycle variable in App.

Introduce three app-scoped owners:

- Session: bootstrap, pairing and connection lifecycle, with typed access state.
- View data: active query, results, cursors, generations, cancellation and queued
  invalidations, building on `loadView()` and `ReadRequests`.
- Navigation: route history and the decision to navigate or preserve an open draft.

Use existing Svelte primitives and explicit dependencies. Construct these owners
once per mounted application. Extract the pairing screen, navigation chrome and
collection displays around meaningful UI responsibilities. Keep independent
dialogs independent; use unions only where alternatives are actually exclusive.

**Done when:** adding a view does not require editing authentication and retry
logic; stale reads cannot update a different route; browser Back/Forward and open
drafts retain their established behavior. Moving the same variables into one
large `app-state.ts` would not meet this criterion.

### 3. Retain validated Rust types beyond the parser

**Priority: high.** Evidence:
[domain models](../../crates/domain/src/models.rs#L190),
[ParsedDocument](../../crates/project-store/src/document.rs#L40),
[workspace read](../../crates/application/src/engine.rs#L146),
[mutation preparation](../../crates/application/src/mutation.rs#L140).

The domain provides `Document`, `Workspace` and `Validated<T>`, but
`ParsedDocument::value()` serializes a validated document into `serde_json::Value`.
`Engine::workspace()` validates a clone and discards the resulting typed value.
Application code then indexes metadata by strings and repeatedly unwraps values.
This makes schema assumptions implicit and prevents the compiler from checking
many ordinary field changes.

Start with a typed, versioned workspace read. Then retain typed documents in
source reads and mutation preparation. Use a small `Versioned<T>` representation
where a value and its source version travel together. Keep raw source bytes where
normalization, conflict checks and recovery require them. Use typed construction
and patch application for individual resource kinds.

JSON remains appropriate for wire boundaries, persisted original command payloads
and explicitly allowed extension values. Preserve `x-*` fields, explicit set/clear
semantics, normalization requirements, source versions and journal digest meaning.
Changing the internal representation must not silently change serialization or
the identity of an existing command.

Do not replace every `unwrap()` mechanically with `?`: some follow validated
invariants or embedded constants. Make the invariant visible in the type so that
the repeated conversion is unnecessary. Introduce distinct ID/version types only
where they prevent a real mix-up; a full domain-framework rewrite is unnecessary.

**Done when:** core resource logic operates on typed fields, while JSON conversion
is concentrated at named boundaries. Existing serialization, extension-preservation,
conflict and fault-injection tests must still pass.

### 4. Give each editor kind a typed draft and complete the API type surface

**Priority: high after the shared command controller.** Evidence:
[editor props and metadata cast](../../apps/web/src/features/editor/Editor.svelte#L35),
[draft snapshot](../../apps/web/src/features/editor/Editor.svelte#L167),
[EditorFields](../../apps/web/src/features/editor/editor-draft.ts#L3),
[editor completion](../../apps/web/src/features/editor/editor-actions.ts#L4),
[contract generator](../../scripts/generate-contracts.mjs#L29).

`Editor.svelte` has 607 script lines and 53 `$state` calls. It accepts an independent
`type: string` and `Resource | null`, casts metadata through `unknown`, and manages
project, card, milestone and report fields together. Fields are listed again in
initialization, dirty-state snapshots and payload construction. Adding a field
requires keeping these representations aligned. The helper extraction is useful,
but it has not yet established a single typed owner for the draft.

Use a discriminated editor target that binds the resource kind to its resource
type and create/edit mode. Give cards, projects, milestones and reports their own
draft shapes and field components, with a shared editor shell for close handling,
errors and command status. Derive initial state, dirty comparison and payload from
the same draft representation. Keep the report composer independently owned so a
posted report cannot erase unsaved card edits.

Carry the command's UI intent explicitly. `editorCompletion()` currently infers
whether to close the editor or refresh focus from the endpoint path; endpoint
renaming should not determine draft lifecycle.

The generator currently selects seven response schemas. Other response shapes,
including planning types and pairing, are handwritten, and request payloads are
mostly `unknown` or `Record<string, unknown>`. Extend generation to the request and
response schemas actually consumed by the app, then expose focused endpoint
functions. `api<T>(path)` currently trusts a caller-chosen type and casts JSON to
it; this is not an endpoint contract or runtime validation. Keep UI draft types
separate from wire types and retain server-side validation.

**Done when:** a card draft cannot carry a project state by accident, mismatched
resource/type props are rejected by TypeScript, and adding a field has one draft
definition and one deliberate wire mapping.

### 5. Enforce the application boundary with a smaller public API

**Priority: medium.** Evidence:
[Engine fields](../../crates/application/src/engine.rs#L25),
[Journal::db](../../crates/application/src/journal.rs#L176),
[command-status handler](../../crates/projectd/src/dispatch.rs#L390),
[application errors](../../crates/application/src/lib.rs#L25),
[transport error mapping](../../crates/projectd/src/lib.rs#L126).

Engine implementations are spread over 12 source modules, but this is largely a
file split around the same shared object. `journal`, `index` and `gate` are public,
and `Journal::db()` exposes a raw connection guard. Production HTTP dispatch reads
the `commands` table and reconstructs its reply itself. Thus a transport handler
knows persistence details that belong to the application.

Add a focused application operation for command status, and expose explicit epoch,
event subscription and job-read operations. Gradually make persistence fields and
raw connection access private to their owning modules. Keep Engine as a public
facade; move registration, project commands, workspace commands and read projections
behind private services as needed. Concrete Rust structs are sufficient unless
there is an actual alternate implementation to support.

Separate internal application errors from transport mapping incrementally.
`AppError::Rejected(Reply)` currently carries an HTTP status and JSON body, while
the context-free `State` variant covers unrelated failures. The transport maps all
other errors to a generic 503 without retaining diagnostic context at that point.
Use meaningful internal categories and operation context, then map to stable
public codes in one place. Persisted journal replies can remain the existing wire
format for compatibility. Record safe internal diagnostics without source bodies,
tokens or credentials.

Document lock ownership and acquisition order before moving methods. Encapsulation
must preserve the workspace gate, project lock and journal transaction boundaries.

**Done when:** adding a transport endpoint needs application methods, not SQL or
lock access, and an internal failure identifies the failed operation while the
public error contract remains stable.

### 6. Make projection code readable as SQL plus mapping plus policy

**Priority: medium; useful early cleanup in isolated changes.** Evidence:
[attention/calendar queries](../../crates/application/src/views/mod.rs#L48),
[summary mapping](../../crates/application/src/index/mod.rs#L44),
[registration-plan changes](../../crates/application/src/engine.rs#L312).

Rust formatting passes, but production Rust still has 93 lines longer than 180
characters. Several combine SQL, closure bodies, extraction and `json!` expressions.
For example, attention/calendar projection closures contain multiple statements
on one line, and registration change construction embeds branching inside JSON
inside an iterator. These are concrete readability costs, not a formatter failure.

Give SQL readable indentation, separate row conversion into named functions or
typed rows, name intermediate concepts, and format complex `json!` bodies by hand.
Use local `.sql` files only for large, mostly static queries where they improve
navigation. Keep parameter binding and bounded filtering/pagination in SQL.

`index.rs` contains database setup, projection updates, invalidation events,
pagination and summaries. Split these responsibilities into private `index/`
modules as they are changed. Its 1,056-line total includes trailing tests; length
alone is not the reason to split it. Preserve the existing snapshot consistency
and targeted refresh semantics.

**Done when:** a reviewer can read a query, its row mapping and its returned shape
separately without changing its filters, ordering, cursor meaning or write behavior.

### 7. Organize by feature and standardize the small repeated UI pieces

**Priority: lower; combine with the changes above.** Evidence:
[global styles in App](../../apps/web/src/App.svelte#L1378),
[DateChange dialog](../../apps/web/src/features/planning/DateChange.svelte#L204),
[MoveChange dialog](../../apps/web/src/features/board/MoveChange.svelte#L179),
[existing modal action](../../apps/web/src/lib/ui/dialog.ts#L1),
[formatting scope](../../package.json#L21),
[browser card suite](../../scripts/browser/suites/card.mjs#L12).

The flat `lib/` combines API transport, state policies, UI primitives and complete
features. Move files with their consumers into feature folders. Keep truly shared
infrastructure small. A useful direction is:

```text
src/
  app/                 # session, navigation, view-data owners, application shell
  features/
    editor/            # editor shell, typed drafts, per-kind field components
    board/
    calendar/
    timeline/          # planning adapters stay with their widget consumers
    tags/
    settings/
  shared/
    api/               # generated contracts, HTTP, reads, command controller
    ui/                # dialog shell, notices, shared form presentation
  styles/              # global tokens, theme and base element rules
```

This is an ownership sketch, not a requirement to create every directory or move
every file in one commit. Keep integration-specific widget CSS and selectors in
their adapter feature. Existing board/date gesture modules are used and have a
clear purpose; their small size does not make them disposable.

Move global tokens/base styles out of App. Reuse dialog surface, backdrop, footer
and error presentation where their semantics match. Retain `modal()` and native
focus behavior; a shared shell must let each feature decide whether closing is
permitted while a command is unresolved. Avoid a generic form-builder framework.

Apply consistent formatting to maintained browser and Node test scripts too; the
current format script covers frontend sources and only two build scripts. Keep
imports together, use one state declaration per logical unit, replace deeply
nested ternaries with named mappings or functions, and prefer descriptive names
in long closures. Short local names in tiny adapters are acceptable.

For tests, extract only repeated fixture setup and reusable operation helpers.
The card browser suite is an 887-line function containing helpers and scenarios;
named scenario functions can improve failure isolation and navigation while
retaining the existing runner. Add pure controller tests during state extraction
and keep browser tests for actual draft, focus, session and gesture integration.
There is no demonstrated need for a new test framework or arbitrary coverage quota.

Do not combine type migration, storage-byte changes, lock changes and UI redesign
in one change. Maintain existing behavior first. Assess success by fewer owners
for each invariant, fewer repeated transition branches and better compiler checks,
not by a target number of files or deleted lines.

## What would add complexity without a demonstrated benefit

A wholesale framework rewrite, a generic repository/DI layer, one interface per
small helper, a universal form/workflow engine, a giant global frontend store and
an ORM solely to hide these queries are not needed to address the findings.

Do not remove validation, version checks, cancellation, uncertainty handling,
normalization or durability code as cosmetic cleanup. These enforce real product
contracts. Do not delete historical evidence or remaining handoff requirements
merely to reduce repository size. The previous work already established an ignored
location for new bulk browser artifacts; continuing that policy is sufficient.
