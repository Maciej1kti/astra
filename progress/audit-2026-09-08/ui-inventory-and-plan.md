# UI inventory and consolidation plan

Audit date: 2026-09-08. Source revision: `c3b912fc122b58780f870ee4da27c2d29411725a`.

This is a source and specification audit. **No observation in this document is a browser test result.** A finding marked “source confirmed” means the implementation contains the described behavior or omission; its visible impact still needs runtime verification. “Source inference” marks a probable outcome that depends on actual event timing, data, browser behavior, or widget behavior. The accompanying browser audit is the authority for reproduced UI defects.

Read: `AGENTS.md`, `START_HERE.md`, `progress/SCOPE.md`, `docs/01-PRODUCT.md`, `docs/08-UI-AND-INTERACTIONS.md`, application Svelte components, gesture adapters, display preferences, relevant list query implementation and OpenAPI parameters. This checkout has no `.project/README.md` or `.project/project.md`; none was initialized. No application code, project data, or server configuration was changed for this sub-audit.

## Assessment

Astra has substantial planning functionality: seven views, a shared resource editor, quick card creation, versioned moves, calendar date ranges, Gantt dependencies and a forecast, focus ordering, reports, history/undo, theme preferences, pairing and diagnostics. Its architectural strengths should survive a redesign: widgets render domain data, resource writes retain versions and command identity, and Markdown rendering avoids raw HTML and remote image fetching.

The main gap is the consistency of everyday work. The shell, shared form, SVAR Board, SVAR Gantt and EventCalendar currently behave like related but distinct tools. Common actions often require a large form, while technical fields and maintenance controls occupy prominent positions. Search scope, selected project scope, save behavior, navigation history, metadata and pagination differ between views. A polished product needs one clear action hierarchy and one predictable resource workflow before it needs more decorative styling.

The recommendation is to preserve all existing domain capabilities, fix the data/draft risks first, then consolidate navigation, actions, editor structure, status/date rendering and feedback. Rare operations belong in an accessible `More` menu or an explicitly named advanced section. Relevant primary actions must remain visible; errors, unsaved drafts and hard-deadline confirmation must never be hidden in a menu.

## Visual and behavioral consolidation

### One visual foundation

The existing light/dark base palette is centralized in `App.svelte:1239–1295`, but spacing, radii, typography and status colors remain local. The proposed token template is a separate, unused naming system (`templates/design-tokens.css`). Do not maintain both as competing foundations.

Adopt one application stylesheet and adapter layer. Suggested semantic token groups:

| Group | Concrete contract |
|---|---|
| Surface | `--surface-app`, `--surface-panel`, `--surface-muted`, `--surface-hover`, `--surface-selected`, `--surface-overlay`; define all in light/dark/system. |
| Text | `--text-primary`, `--text-secondary`, `--text-muted`, `--text-on-accent`, `--text-disabled`; use one system sans font throughout working screens. Reserve serif styling, if retained, for onboarding only. |
| Borders/focus | `--border-subtle`, `--border-default`, `--border-strong`, `--focus-ring`; focus must remain distinct from selection. |
| Semantic states | Named foreground/background/border tokens for planned, active, review, done, cancelled, blocked, warning, error, success; preserve text/icon meaning. Map project/milestone states into labels without changing domain semantics. |
| Date meaning | Separate `plan`, `target-date`, `hard-deadline`, `review-date`, `forecast`; never overload one unlabeled “date” chip. |
| Spacing/type | 4/8/12/16/24/32px spacing; default content 14px desktop, 16px readable mobile form fields; labels 12–13px; primary view title 22–26px. Avoid 7–10px labels for essential information. |
| Control geometry | Normal desktop control 36–40px when pointer precision allows; coarse-pointer targets at least 44×44px; panel gap 16–24px; row density presets only if validated with real content. |
| Layers/motion | 6px control radius, 8px panels, 10px dialogs; one overlay/backdrop and z-index scale; 140ms feedback/180ms panel transitions; reduced motion removes travel animation, without delaying direct gesture preview. |

Map SVAR and EventCalendar variables to those semantic tokens in named adapters. Keep vendored widget CSS isolated. Do not scatter undocumented `.wx-*` overrides across features; the existing adapters depend on internal widget classes for scroll, card footer insertion and chart behavior (`Board.svelte:293–337`, `GanttView.svelte:293–305`, `596–600`). Record those dependencies and verify them on upgrades.

Dangerous or irreversible actions have distinct treatment; do not make every reversible status change look destructive.

### One mutation and draft model

Define a UI-level action object with `id`, human label, scope/resource type, visibility, enabled state and reason, shortcut, confirmation rule, versioned intent and post-success behavior. All entry points call the same action handlers. Card More, keyboard, Board drag and inspector fields must share the domain intent, validation and feedback model.

Use these explicit states: `clean`, `dirty`, `submitting`, `confirmed`, `uncertain`, `conflict`, `saved_with_warning`, `access_lost`. Keep the base resource separate from draft fields and pending command identity. A successful independent action such as Pin must not automatically call the resource editor's “saved and close” callback. Page refresh must not replace a dirty draft. While a command is uncertain, freeze the submitted intent and prevent a different Save for that intent; allow copying the draft and inspecting details. Confirmation of one command must not imply all currently typed fields were saved.

Normal feedback should say what happened: “Pinned to Focus”, “Moved to Active”, “Plan changed to 12–14 September”, or “Saved; the rest of the view is updating.” Request IDs, epochs and raw server payloads remain available under Details, except where an unresolved operation requires preserving its identity. Keep error copy separate from success copy; currently “Draft copied” is stored in an `error` variable and rendered as an alert (`Editor.svelte:133`, `673–675`; equivalent patterns in proposal/settings dialogs).

### Navigation, search and context

Use explicit route state for view, project, selected resource, resource collection, search/filter/sort, calendar date/layout and timeline scale. Intentional view/resource navigation should be back/forward navigable. Typing may replace current search state to avoid one history entry per keystroke. Persist only browser display preferences in local storage; keep secrets and resource drafts out of URL state.

Give workspace Focus an intentional scope. Either project/search filter all displayed items or the UI clearly separates “Workspace Focus” from “Attention in this project”; a single unlabeled selector must not produce both interpretations. Use complete server totals where available. Label any bounded analysis or loaded-page count honestly.

Choose one search contract: global search for full content, with a separate scoped Filter if needed. If Board cannot server-filter while preserving complete neighbor information, render search results as a list or explicitly disable reordering and explain why. Never infer rank from filtered neighbors. Reset pagination only on a user-visible scope change, or preserve an anchor when external writes make cursors stale.

### Keyboard, phone and scrolling

Keep native modal focus/inert handling. Add one documented Cmd/Ctrl+K command palette outside editing fields, Cmd/Ctrl+Enter save in an editor when validation permits, Escape for the current layer/gesture, and visible menu equivalents for every shortcut. Do not hijack browser Find, native undo in text fields, or operating-system shortcuts. Navigation should expose `aria-current`; lists/tables need meaningful semantics and headers. Announce mutation results once through a shared polite live region, with errors attached to their fields.

Use a single responsive rule set: navigation rail on desktop, collapsed rail/drawer on tablet, compact top header and a small set of primary destinations plus More on phone. All seven views remain reachable. Reorderable Board and Gantt stay within named scroll regions; the document must not gain horizontal overflow. Preserve the Board's per-project scroll/collapse behavior while applying similar view-state treatment elsewhere.

The phone inspector should fill the dynamic viewport, have a sticky title/actions region, scroll its content, and account for safe-area insets and software keyboard. Use at least 44×44px targets for touch controls and let ordinary content scroll before drag is armed. Test long-press selection, second finger, pointer cancellation, lost capture, Escape, blur, orientation change and session termination. Board already handles more cancel events than the date adapter (`board-gesture.ts:216–217` versus `date-gesture.ts:115–116`); consolidate the lifecycle while keeping widget-specific mechanics.

On narrow Timeline, keep a compact selected-card title/status/dates summary beside controls and use one understandable horizontal time navigation surface. Offer a list/agenda alternative at the same capability level, not a mobile read-only mode. Browser emulation is useful for layout; it cannot establish physical iPhone touch performance or software-keyboard ergonomics.

## Phased delivery and acceptance

These are proposed implementation phases, not completed fixes and not an authorization to expand the currently frozen Kanban scope. The existing owner decisions in `progress/SCOPE.md` still apply; bug fixes and verification remain appropriate, while new Board features must be separately chosen.

| Phase | Deliverable | Acceptance gate |
|---|---|---|
| 0 — Reproduce and protect core workflows | Regression scenarios for UI-S01/S02/S03 and browser-confirmed defects; isolate create intent, draft lifecycle and archive recovery. | No independent pin/read/history action loses unsaved fields. Add type matches current view. An archived synthetic card can be found and restored through UI. Tests proving a data-loss fix run before and after the change. |
| 1 — Foundation and shell | Semantic tokens, widget adapters, shared controls/dialog anatomy, compact header, workspace/project menus, direct mobile sign out and visible host. | At 390, 768, 1280 and 1440px, light/dark/system: no document-level horizontal overflow; one recognizable primary action; host and sign out reachable; all widget tokens resolve; text, focus and controls pass measured contrast checks. |
| 2 — Card model, shared inspector and actions | CARD-01 purpose/content/relationships/lifecycle; common resource actions, progressive disclosure, named relationship pickers, tag selection/chips, clear mutation feedback, field-level errors and conflict review. | A title-only card can grow into a complete outcome/decision record with acceptance context and targeted updates. Status/plan/deadline/focus/update/archive use consistent labels and Save rules. Related titles replace IDs; tag input prevents accidental duplicates. Conflict review preserves current and draft values without force-write. |
| 3 — Tag management, retrieval and context | TAG-01 scope/naming contract, tag discovery/management and full-scope filters; archive browser, search, truthful totals, route/history and page/scroll preservation. | Complete TAG-01 add/remove/filter/rename/merge scenarios with explicit per-resource outcomes; cards beyond page one remain findable. Filters apply consistently; reload and Back/Forward preserve calendar period/layout/resource; unrelated updates do not unexpectedly reset reading context. |
| 4 — Planning ergonomics | Common date badges/proposals; coherent Board/date gesture feedback; selected-card Timeline summary; more accessible dependency flow; readable overlap and long titles. | Move preserves inclusive duration; either resize edge updates only that boundary; month/year transitions work; hard deadlines stay unchanged without explicit confirmation; invalid/cyclic dependency causes a readable error and no accidental extra write. |
| 5 — Cross-platform acceptance | Populated-data walkthrough; keyboard/screen-reader checks; real iPhone and target desktop browser tests; narrow/zoom/landscape/keyboard/offline/reconnect. | Complete all core workflows without pointer-only requirements, trapped focus or hidden Save; physical phone touch and long scrolling pass with recorded device/browser; pending/conflict outcomes preserve draft and command identity; every defect is linked to evidence or explicitly remains open. |

Measure a practical workflow budget after the redesign: create a title-only card in one compact entry flow; change status in at most two explicit selections; pin or unpin from a contextual action without navigating away; open related milestone/dependency by title; edit a schedule without scrolling through JSON/history; restore an archived card without a CLI. Record clicks/keystrokes and time on the same synthetic scenarios before and after. These are proposed product acceptance targets, not current measured performance.

## Feature opportunities and scope boundaries

The most valuable near-term additions are improvements to existing work: server-backed filters, sort, saved views, archive/restore discovery, title-based relationship selection, contextual decision resolution, actionable project summaries (goal/phase/next milestone/latest meaningful update), consistent command search, and optional multi-selection for safe repetitive edits. A backend batch/version design is required before promising bulk writes; UI selection alone is insufficient.

Source omissions should not be confused with competitor-driven obligations. Repeating tasks, time blocking, resource/capacity planning, team roles, attachments, rich-text editing, offline synchronization, push notifications, integrations and public sharing are explicitly outside the current product scope in `docs/01-PRODUCT.md`. Built-in backup/restore archives and general source migration are explicitly deferred in `progress/SCOPE.md`. They can be discussed as future strategic options, but should not be reported as broken v1 functions or added as empty menu items.

Keep differentiated strengths visible in the finished product: project context attached to an explicitly selected local folder, a shared human/agent model, explainable attention signals, dates that distinguish plan from deadline, append-only decisions/corrections, and reliable versioned writes. Professional UI consolidation should make these easier to use; it should not obscure them behind a generic task-board appearance.
